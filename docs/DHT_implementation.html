Overview

The DHT (Distributed Hash Table) in c-toxcore is a Kademlia-like overlay network that enables peer discovery in the Tox messaging protocol. It provides a way for nodes to find each other's IP addresses using only their long-term public keys, without requiring a central server.

The implementation follows the principles of the BitTorrent DHT (BEP 0005) but with a simplified, encrypted packet format and NAT traversal capabilities.

Ping Packet

Request:  0x00 | sender_pubkey[32] | nonce[24] | encrypt(type=0 | ping_id[8])
Response: 0x01 | sender_pubkey[32] | nonce[24] | encrypt(type=1 | ping_id[8])

Total size: 82 bytes (1 + 32 + 24 + 1 + 8 + 16 = 82)

Ping IDs are stored in a Ping_Array with a 5-second timeout (PING_TIMEOUT).

Nodes Request Packet

0x02 | sender_pubkey[32] | nonce[24] | encrypt(target_node_id[32] | sendback_data[8])

Nodes Response Packet

0x04 | sender_pubkey[32] | nonce[24] | encrypt(num_nodes | nodes[] | sendback_data[8])

The response contains up to 4 nodes (MAX_SENT_NODES) closest to the requested target.

Core Algorithms

Kademlia-like Routing

The DHT organizes nodes by XOR distance between their 256-bit public keys. The distance metric is: 

distance(a, b) = a XOR b  (treated as a 256-bit integer)

Close List

The close_clientlist has 1024 slots organized as 128 buckets × 8 nodes. Bucket i (0–127) contains nodes where the first differing bit from our key falls in bit range [i*8, i*8+7].

A node is added to the close list if:

  • Its XOR distance to our key lands it in a non-full bucket, or
  • It is closer than the worst node in the appropriate bucket

The first differing bit determines the bucket. The total XOR distance determines ordering within a bucket.

XOR Comparison Functions

  • bit_by_bit_cmp(pk1, pk2) — returns the index of the first differing bit (MSB, 0-indexed).
  • id_closest(pk, pk1, pk2) — returns 0 equal distance, 1 if pk1 closer, 2 if pk2 closer.

Bootstrap Process

  1. Initial bootstrap: dht_bootstrap() sends a NET_PACKET_NODES_REQUEST to a known bootstrap node.
  2. Post-load bootstrap: dht_connect_after_load() bootstraps from up to 8 previously saved nodes in round-robin fashion, stopping once dht_non_lan_connected() returns true.
  3. Aggressive bootstrap: For each friend, up to MAX_BOOTSTRAP_TIMES (5) extra nodes requests are sent aggressively before settling into the routine interval.

Peer Discovery (Iterative Lookup)

For each friend in friends_list[], the DHT periodically sends nodes requests:

  • Every 20 seconds (NODES_REQUEST_INTERVAL): to a random good node from the friend's client list.
  • Every 60 seconds (PING_INTERVAL): to every node in both the close list and friend client lists (combined ping + nodes request).

When a nodes response arrives:

  1. The ping ID is verified.
  2. The responder is added via addto_lists().
  3. Each returned node is queued for pinging via the to_ping buffer.
  4. Return IP information is updated for NAT traversal.

get_close_nodes()

Searches both close_clientlist and every friend's client_list to find up to 4 nodes closest to a target public key. Features:

  • IPv4/IPv6 filtering
  • LAN IP filtering when requester is not on LAN
  • Optional announce-node-only filtering (CHECK_ANNOUNCE_NODE)

Ping System

Anti-Amplification Design

The ping system in ping.c prevents amplification attacks through a to_ping buffer:

  1. When a node sends us a valid packet, ping_add() adds it to a buffer (max 32 entries).
  2. Every 2 seconds (TIME_TO_PING), ping_iterate() sends actual ping requests to all buffered nodes.
  3. This ensures we never initiate contact with a node that didn't contact us first.

Ping Flow

  1. Generate a random 64-bit ping ID, store {public_key, IP_Port} in ping_array (5s timeout).
  2. Encrypt with ECDH-derived shared key, send as NET_PACKET_PING_REQUEST.
  3. Receiver decrypts, sends back NET_PACKET_PING_RESPONSE with same ping ID, and calls ping_add().
  4. We verify the ping ID, confirm source IP/port matches, then call addto_lists().

Combined Pings + Nodes Requests

In do_ping_and_sendnode_requests(), nodes requests double as pings: every 60 seconds, every node gets a nodes request serving as both a liveness check and a lookup for closer nodes.

NAT Hole Punching

Prerequisites

  • hole_punching_enabled must be true.
  • At least MAX_FRIEND_CLIENTS / 2 (4) nodes report the same friend IP.
  • The friend must be "online" (nodes returning their IPs).

Protocol

Uses CRYPTO_PACKET_NAT_PING (ID 254):

  • Request (type 0): broadcast via route_to_friend() to all nodes claiming to know the friend.
  • Response (type 1): sent via routeone_to_friend() to a single node.

Punching Algorithm (punch_holes())

Phase 1 (first 5 tries):

  • If all reported ports are the same: ping that port directly.
  • If ports differ: iterate 48 attempts alternating around known ports.

Phase 2 (after 5+ tries): brute-force scan starting from port 1024, 48 pings per cycle.

If no success after 40s (PUNCH_RESET_TIME), all counters reset.

do_nat() Loop

Runs every do_dht() cycle:

  • Every 3s (PUNCH_INTERVAL): send NAT ping request for each friend with enough returned IPs.
  • If hole punching active AND we received a ping within 6s: find common IP via nat_commonip(), call punch_holes().

Close List and Friend List Relationship

Close List (close_clientlist[1024])

  • Nodes closest to our own DHT public key.
  • 128 buckets, 8 nodes per bucket. Bucket determined by first differing bit.
  • Used for routing, nodes responses, connectivity detection.

Friend List (friends_list[])

  • One entry per friend. Each has client_list[8] of nodes closest to the friend's key.
  • Nodes report the friend's current IP via ret_ip_port.
  • A friend is "found" when its public key appears in its own client_list with a valid association.

addto_lists()

Called on any valid packet from a node. Adds/updates in:

  1. The close_clientlist (via add_to_close()).
  2. Every friend's client_list where the node is in range (via replace_all()).

Node Replacement (replace_all())

Within each friend's client_list[8], nodes sorted by:

  1. Non-timed-out nodes first (by XOR distance).
  2. Timed-out nodes last (by XOR distance).

A new node replaces an existing one if: there is a bad slot, or the new node is XOR-closer to the friend than the furthest good node.

Fake Friends

DHT_FAKE_FRIEND_NUMBER (2) random keypairs are added on DHT creation for onion path routing, preventing real friend info from leaking.

Connectivity Detection

  • dht_isconnected(): true if any close list entry has a non-timed-out association.
  • dht_non_lan_connected(): true if any close list entry has a non-timed-out, non-LAN association.

Onion Routing Integration

Onion Path Construction

3 DHT nodes are selected per 3-hop path:

  • randfriends_nodes() — from fake friends' client lists (avoids leaking real friends).
  • closelist_nodes() — from the close client list.
  • create_onion_path() assembles the path with ephemeral keypairs per hop.

Announce Protocol

Clients announce to 12 DHT nodes via 3-hop onion paths. The announce server stores: real public key, 3-layer encrypted return path, data encryption key. Entries expire after 300s (ONION_ANNOUNCE_TIMEOUT).

Data Delivery

To reach a friend whose IP is unknown: send an onion data request to a server the friend announced to; the server wraps the data along the stored return path; the friend receives it through 3 layers of decryption.

DHT Public Key Exchange

Friends exchange temporary DHT public keys via onion data packets (ONION_DATA_DHTPK = 156). Sent every 30s via onion and every 20s via direct DHT.

TCP Relay Integration

TCP relays have DHT public keys and use special address families (TOX_TCP_INET = 130, TOX_TCP_INET6 = 138).

  • TCP relay info is exchanged between friends via onion data packets.
  • When UDP is unavailable, onion paths can use TCP relays.
  • 3 TCP connections are reserved for onion use.
  • tcp_send_onion_request() sends onion packets via TCP relays.

Cryptography

All primitives use NaCl/libsodium:

Packet Encryption

  • DHT packets: ECDH key exchange → shared key → symmetric encryption.
  • Shared_Key_Cache caches ECDH results (600s timeout).
  • Onion packets: ephemeral keypairs per hop.
  • Ping IDs encrypted with ECDH-derived shared keys.

Saving and Loading

  • dht_save() — serializes close client list and friend data.
  • dht_load() — restores state and queues saved nodes for bootstrap.
  • dht_size() — returns serialized size.

Concrete Walkthrough: Two Clients Behind Tor Finding Each Other

This section traces a real scenario end-to-end: two bootstrap relays R1 and R2 that are each reachable via both a clearnet IP and a Tor onion address; two clients A and B, each behind Tor, each contacting a different relay; both clients wanting to find each other.

Setup

  • R1, R2 — bootstrap relays. Each runs a Tox node with a DHT public key and a TCP relay server. Each has a clearnet IP and a Tor onion address (.onion).
  • A, B — clients. Each configured with TOX_PROXY_TYPE_SOCKS5 pointing to 127.0.0.1:9050.

Layer 1: no UDP

Because a SOCKS5 proxy is configured, c-toxcore disables UDP entirely (tox_options.h:130-131). All communication goes over TCP relay connections through Tor.

A → SOCKS5 → Tor → R1.onion:33445   (TCP relay connection)
B → SOCKS5 → Tor → R2.onion:33445   (TCP relay connection)

Step 1: Bootstrap

A calls dht_bootstrap_from_address("R1.onion", 33445, R1_pubkey).

This resolves the hostname, opens a TCP connection through Tor's SOCKS5 proxy to R1.onion:33445, and performs the TCP relay handshake:

  1. Cookie request/response (NET_PACKET_COOKIE_REQUEST / NET_PACKET_COOKIE_RESPONSE) — obtains a temporary cookie for the crypto handshake.
  2. Crypto handshake (NET_PACKET_CRYPTO_HS) — establishes an encrypted session with R1's TCP relay server.
  3. TCP relay registration — A is now a connected TCP relay client. R1 knows A's Tor IP and can route packets to A.

Same flow for B → R2.

Step 2: Populating the DHT routing table

A sends NET_PACKET_NODES_REQUEST to R1. Under Tor, this packet is serialized and sent over the TCP relay connection using tcp_send_onion_request().

R1's handle_nodes_request() (DHT.c:1363) decrypts the request, extracts the target public key (A's own key in this case — asking "who is close to me?"), and calls send_nodes_response().

What send_nodes_response() does (DHT.c:1313)

// 1. Get up to 4 nodes closest to the requested key
Node_format nodes_list[MAX_SENT_NODES];  // MAX_SENT_NODES = 4
uint32_t num_nodes = get_close_nodes(dht, client_id, nodes_list,
    net_family_unspec(), ip_is_lan(&source->ip), false);

// 2. Pack them into the response
int nodes_length = pack_nodes(..., nodes_list, num_nodes);

// 3. Send: [0x04][sender_pubkey[32]][nonce[24]][encrypted payload]
// Payload: [num_nodes(1 byte)][packed nodes][sendback_data(8 bytes)]
sendpacket(dht->net, source, data, len);

get_close_nodes() scans TWO data structures (DHT.c:729)

First: the close_clientlist[1024] (R1's 128 buckets × 8 nodes closest to R1's own key).

Second: every friend's client_list[8] (R1's friends lists).

For each entry, get_close_nodes_inner() (DHT.c:635) checks:

1. Is the node's association non-timed-out? (timestamp + 122s > now)
2. Is the address family right? (IPv4/IPv6/unspec)
3. Is LAN IP allowed? (depends if requester is on LAN)
4. If want_announce: does node support announce protocol?

If all checks pass, the node is added to a list of up to 4 entries using XOR-distance sorting.

How "closest" is computed — pure XOR on public keys only

The function id_closest() (DHT.c:218):

int id_closest(const uint8_t *pk, const uint8_t *pk1, const uint8_t *pk2) {
    for (size_t i = 0; i < 32; ++i) {
        uint8_t distance1 = pk[i] ^ pk1[i];
        uint8_t distance2 = pk[i] ^ pk2[i];
        if (distance1 < distance2) return 1;  // pk1 is closer
        if (distance1 > distance2) return 2;  // pk2 is closer
    }
    return 0;  // equal
}

Byte-by-byte XOR from index 0 (MSB) to index 31 (LSB). The first byte where the XOR differs determines which node is closer — equivalent to comparing 256-bit XOR distances as big-endian integers, short-circuited at the first differing byte.

IP addresses are NOT used in the distance calculation. Only the public key matters.

What is actually returned — Node_format (key + IP together)

Each entry in the response is a Node_format:

typedef struct Node_format {
    uint8_t  public_key[32];   // The node's DHT public key
    IP_Port  ip_port;          // IP:port where R1 last successfully pinged this node
} Node_format;

The ip_port is the node's own listening address as last verified by R1 — NOT a "friend's return address".

Concrete wire format for up to 4 nodes:

[0x04]                    -- packet type
[sender_pubkey 32 bytes]  -- R1's public key
[nonce 24 bytes]
[encrypted:
  [num_nodes 1 byte]      -- 0 to 4
  [node 1:
    [family 1 byte]       -- 2=IPv4, 10=IPv6
    [IP 4 or 16 bytes]
    [port 2 bytes]
    [public_key 32 bytes]
  ]
  [node 2 ... up to 4]
  [sendback_data 8 bytes] -- echoes the ping_id from the request
]

Example: A asks for nodes close to A's key. R1 has:

NodeXOR distance to A's keyIP:port (where R1 sees them)
NodeX0x00…05203.0.113.1:33445
NodeY0x00…42198.51.100.9:22845
NodeZ0x01…00192.0.2.77:33445

R1 returns: [NodeX(pubkey, 203.0.113.1:33445), NodeY(pubkey, 198.51.100.9:22845)]

How A processes the response

handle_nodes_response() (DHT.c:1484):

// 1. Decrypt, verify ping_id matches what we sent
// 2. Unpack the nodes
// 3. Add the responder (R1) to our lists
addto_lists(dht, source, packet+1);
// 4. For each returned node, queue for pinging
for (i = 0; i < num_nodes; i++)
    ping_node_from_nodes_response_ok(dht, ...);

addto_lists() inserts R1 into A's close_clientlist. The returned nodes go through ping_add() into the to_ping buffer. Every 2 seconds, ping_iterate() sends actual ping requests to each.

A then sends nodes-requests to those newly discovered nodes, repeating the process. Within seconds, A's routing table is populated.

Key: Under Tor, all these packets travel through TCP relay chains, not as raw UDP datagrams.

Step 3: Adding a friend

A calls dht_addfriend(dht, B_pubkey, ip_callback, ...).

This creates a DHT_Friend entry in A's friends_list[]:

struct DHT_Friend {
    uint8_t     public_key[32];          // B's DHT public key
    Client_data client_list[8];          // 8 slots, initially empty
    uint64_t    last_nodes_request;      // 0 → will send immediately
    uint32_t    bootstrap_times;         // 0
    NAT         nat;                     // hole punching state (unused under Tor)
};

Step 4: Iterative lookup for B

A's do_dht_friends() runs every do_dht() tick:

static void do_dht_friends(DHT *dht) {
    for (size_t i = 0; i < dht->num_friends; ++i) {
        // Send any queued bootstrap nodes
        for (size_t j = 0; j < dht_friend->num_to_bootstrap; ++j)
            dht_send_nodes_request(dht, &to_bootstrap[j], friend_pk);

        // Main loop: ping + nodes-request
        do_ping_and_sendnode_requests(dht, &last_nodes_request,
            friend_pk, client_list, MAX_FRIEND_CLIENTS,
            &bootstrap_times, true);
    }
}

Every 60s (PING_INTERVAL): For every node in B's client_list[8] that hasn't hit KILL_NODE_TIMEOUT (182s), send a nodes-request (doubles as keepalive).

Every 20s (NODES_REQUEST_INTERVAL): Pick a random good node from B's list and send a nodes-request to discover closer nodes.

Each response returns up to 4 nodes. addto_lists() inserts them into close_clientlist and B's client_list[8]. The replace_all() function keeps the list sorted by XOR distance to B's key.

Step 5: ret_ip_port — how A learns B's alleged IP

Every node in B's client_list[8] stores an IPPTsPng structure. The field ret_ip_port contains the IP that the node claims B has.

When A pings a node N in B's client list, N responds. A's handle_ping_response() calls addto_lists(), which triggers update_client_data():

assoc->ret_ip_port = received_ip_port;  // "N says B is at this IP"
assoc->ret_timestamp = now;

friend_iplist() collects all non-timed-out ret_ip_port values. If at least 4 of 8 nodes agree on an IP, that IP is considered B's current address.

When B's own public key appears in its own client_list[8], the ip_callback fires:

if (pk_equal(public_key, dht_friend->public_key)) {
    callback(data, number, &ip_port);  // "Found B at X:Y!"
}

Step 6: Why direct DHT doesn't work under Tor

Under clearnet, route_to_friend() would now send UDP packets to those IPs. Under Tor, UDP is blocked. c-toxcore falls back to the onion routing layer.

Step 7: Onion path construction

A builds 3-hop onion paths through known DHT nodes:

int create_onion_path(Onion *onion, Onion_Path *path, ...) {
    Node_format nodes[ONION_PATH_LENGTH];  // 3 nodes
    randfriends_nodes(dht, nodes, ...);     // from fake friends (privacy!)
    for (i = 0; i < ONION_PATH_LENGTH; i++) {
        random_keypair(...);
        encrypt_precompute(...);            // ECDH shared key
        path->ip_port[i] = nodes[i].ip_port;
        path->node_public_key[i] = nodes[i].public_key;
    }
}

Each path: A → Hop1 → Hop2 → Hop3 → destination

A maintains 6 paths (NUMBER_ONION_PATHS), refreshing every 20 minutes (ONION_PATH_MAX_LIFETIME). Under Tor, these packets are sent via TCP relay connections using tcp_send_onion_request().

Step 8: Announce protocol

A announces itself to 12 (MAX_ONION_CLIENTS_ANNOUNCE) DHT nodes through 3-hop paths. The announce request contains:

struct announce_request {
    uint8_t real_pk[32];           // A's long-term public key
    uint8_t data_pk[32];           // Data encryption key
    uint8_t sendback_data[ONION_RETURN_3];  // 3-hop encrypted return path
};

The server stores an Onion_Announce_Entry (expires after 300s, refreshed periodically). B does the same.

Step 9: DHT public key exchange

Temporary DHT public keys are exchanged so route_to_friend() can work:

Via onion (every 30s): send_onion_data() encrypts the DHT key with B's long-term key, sends through onion paths to B's announce servers, which forward along B's return path.

Via DHT (every 20s): route_to_friend() broadcasts to all IPs in B's client list (relayed through TCP connections under Tor).

Step 10: Data delivery

Path 1 — Onion routing (works under Tor):

A creates message → send_onion_data()
  → picks a valid announce server of B
  → sends through 3-hop path
  → server wraps in NET_PACKET_ONION_DATA_RESPONSE
  → travels back via B's 3-hop return path
  → B receives & decrypts

Path 2 — Direct DHT (works over clearnet UDP):

A calls route_to_friend(B_dht_pk, packet)
  → friend_iplist() collects ret_ip_port from B's 8 nodes
  → sends packet to each alleged IP simultaneously
  → NAT hole punching (punch_holes()) makes it bidirectional

Under clearnet, Path 2 is preferred (lower latency). Under Tor, only Path 1 works.

Step 11: Lossless crypto connection

A sends: NET_PACKET_CRYPTO_HS (cookie + DH public key)
B responds: NET_PACKET_CRYPTO_HS (cookie + DH public key)
→ Both derive session keys
→ A sends NET_PACKET_CRYPTO_DATA (data + ACKs)
→ Connection established

This handshake works over either the onion path or the DHT path.

The DHT's fundamental job — finding nodes that are XOR-close to a target key — is the same regardless of transport. Under clearnet UDP, the result is direct IP discovery + NAT hole punching. Under Tor, the result is a populated routing table that enables onion path construction.

Implementation Plan: Tor-Only DHT with Onion Addresses

This section describes the changes needed to make the DHT operate exclusively over Tor, using .onion addresses instead of clearnet IP addresses. All UDP-based transport is replaced with TCP connections through Tor's SOCKS5 proxy. NAT hole punching is removed. The DHT routing table stores onion addresses.

Why this is needed

Currently Node_format carries an IP_Port which holds a clearnet IPv4/IPv6 address:

typedef struct Node_format {
    uint8_t  public_key[32];       // Curve25519 DHT key
    IP_Port  ip_port;              // clearnet IP + port (19 bytes)
} Node_format;

Tor onion addresses (v3) are 56 base32 characters, decoded to 35 bytes — too large for the existing IP union (which only has 16 bytes for IP6). The entire addressing layer needs to be extended.

Phase 1: Onion address representation

1a. New constants in network.h

#define ONION_V3_ADDRESS_SIZE     35   // decoded .onion v3 address bytes
#define SIZE_ONION                ONION_V3_ADDRESS_SIZE

1b. Extend IP to hold onion addresses

Current IP is 17 bytes (1 family + 16 ip6). Increase the union:

    IP6      v6;                      // 16 bytes
    uint8_t  onion[ONION_V3_ADDRESS_SIZE];  // 35 bytes
} IP_Union;

typedef struct IP {
    Family   family;
    IP_Union ip;
} IP;

IP becomes 36 bytes instead of 17. IP_Port becomes 38 bytes instead of 19.

Key design decisions

  1. Extend IP instead of separate Onion_Addr — because IP_Port is used everywhere. One change propagates through all existing code paths.
  2. Connection pool instead of one connection per packet — Tor circuit creation is expensive (~1-2s). Reusing connections to close list neighbors reduces latency.
  3. Not reusing TCP_Client_Connection — The TCP relay protocol is designed for routing connections to other peers. For direct DHT node-to-node communication, simple length-prefixed framing is sufficient and avoids relay protocol overhead.
  4. Remove ret_ip_port — Under Tor, the concept of a "public IP" is irrelevant. Tor hidden services provide connectivity regardless of the client's actual IP.
  5. Onion routing layer (3-hop) can be simplified — Tor already provides multi-hop anonymity. The 3-hop Tox onion path is redundant over Tor but can be kept for incremental adoption.
